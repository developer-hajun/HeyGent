# Feature Development

## 문서 목적

- capability 제거 2차 작업에서 API, 런타임, 저장소의 진입 실행자 필드를 `entry_executor_key`로 전환하는 기준을 기록한다.
- 새 코드, 새 응답, DB schema 모두 executor 용어만 사용한다.
- 아직 운영 DB가 연결되지 않은 상태이므로 호환 컬럼과 legacy fallback 을 두지 않는다.

## 기능 요약

- 기능명: TaskRun 진입 실행자 필드 `entry_executor_key` 전환
- 요청 배경: capability 개념을 제거하고 실행 코드 단위는 executor로 유지하기로 결정했다.
- 해결하려는 문제: 1차 리네이밍 이후에도 API/DB/테스트 일부에 이전 진입 필드명이 남아 새 구조의 기준 필드가 불명확했다.
- 최종 목표 동작: Task 생성, orchestration detail, child delegation, CLI 표시, API 응답은 `entry_executor_key`를 기준으로 동작한다.

- 기준 브랜치: `AI-feat/오케스트레이션-구조-확인`

- 관련 이슈 또는 대화: capability 제거 목적에 맞춰 확인할 점을 정리한 뒤, 2차 작업으로 코드와 기획서를 함께 작성하기로 한 대화
- 검증 기준: `AI\.venv\Scripts\pytest.exe AI\tests -q`

## 왜 필요한가

- 문제 상황: `CapabilitySpec` 계층은 executor로 정리됐지만, TaskRun 진입 필드에 이전 명칭이 남아 노출될 수 있었다.
- 기존 구조의 한계: capability라는 이름이 skill, tool, executor의 역할 경계를 다시 흐린다.
- 이 기능이 들어가면 좋아지는 점: TaskRun에서 “처음 어떤 실행 코드로 들어갔는지”를 executor key로 일관되게 추적할 수 있다.
- 하지 않으면 남는 리스크: 이후 worker나 skill/tool 연결을 붙일 때 capability 명칭이 다시 실행 단위처럼 확산된다.

## 구현 범위

### In Scope

- API 요청에 `entry_executor_key`를 추가하고, 응답에서는 `entry_executor_key`만 노출한다.
- DB schema, API request, TaskRun 도메인 모델에서 진입 실행자 필드를 `entry_executor_key` 하나로 통일한다.
- TaskRun 저장소에 `entry_executor_key` 컬럼과 migration 을 추가한다.
- runtime planning, delegation, CLI, 테스트 fixture를 executor 기준으로 전환한다.

### Out Of Scope

- 기존 운영 DB 데이터 migration
- executor 내부에서 사용하는 skill/tool 구조 변경

## 커밋 가능한 작업 단위

## 1. API/도메인 진입 필드 전환

만들기 위한 기능:

- TaskRun 진입 실행자 필드를 `entry_executor_key`로 고정한다.

주요 생성/변경 파일:

- `AI/app/contracts/task/task_request.py`
- `AI/app/contracts/task/task_response.py`
- `AI/app/domain/tasks/models/task_run.py`
- `AI/app/domain/orchestration/contracts.py`
- `AI/app/domain/orchestration/runtime_planning/planner.py`
- `AI/app/tools/contracts.py`
- `AI/app/tools/registry/registry.py`

파일별 변경 이유:

- `task_request.py`: 시작 executor key 요청 필드를 고정한다.
- `task_response.py`: API 응답의 진입 실행자 필드를 executor key 로 고정한다.
- `task_run.py`: TaskRun 도메인 모델의 진입 필드를 하나로 유지한다.
- `contracts.py`, `planner.py`: orchestration detail 을 `entryExecutorKey` 기준으로 생성한다.
- `contracts.py`, `registry.py`: executor spec 의 진입 key 명칭을 통일한다.

구현 내용:

- `entry_executor_key`를 canonical 필드로 추가한다.
- orchestration detail 의 진입 실행자 metadata 를 `entryExecutorKey`로만 생성한다.

검증 방법:

- API runtime 테스트에서 응답 필드와 orchestration detail 을 확인한다.

완료 기준:

- 새 Task 생성 응답에 `entry_executor_key`가 있다.
- app/test 코드에서 이전 진입 필드명이 검색되지 않는다.

## 2. 저장소/마이그레이션 호환 전환

만들기 위한 기능:

- 새 DB schema 에 `entry_executor_key`만 저장하고 읽는다.

주요 생성/변경 파일:

- `AI/app/storage/queries/task_queries.py`
- `AI/app/storage/migrations/runtime.py`
- `AI/app/storage/sqlite/repository.py`
- `AI/tests/storage/test_sqlite_repository.py`

파일별 변경 이유:

- `task_queries.py`: 새 DB 생성 시 `entry_executor_key` 컬럼을 포함한다.
- `runtime.py`: 기존 DB에 새 컬럼을 추가하는 migration 을 남긴다.
- `repository.py`: 저장 시 canonical 값을 쓰고, 읽을 때 legacy 값을 fallback 한다.
- `test_sqlite_repository.py`: 신규/레거시 입력 모두에서 `entry_executor_key`를 복원하는지 검증한다.

구현 내용:

- `task_runs.entry_executor_key` 컬럼을 추가한다.
- 저장 시 `entry_executor_key`를 우선 저장한다.
- 저장소 insert/update/select 경로에서 `entry_executor_key`만 사용한다.

검증 방법:

- SQLite repository 테스트에서 신규 Task와 legacy Task를 함께 저장/조회한다.

완료 기준:

- 신규 Task 조회 결과의 `entry_executor_key`가 채워진다.

## 3. 런타임/위임/UI/테스트 정리

만들기 위한 기능:

- 실행 경로와 사용자 표시에서 executor 명칭만 사용하게 한다.

주요 생성/변경 파일:

- `AI/app/domain/orchestration/agent/tool_calling_loop.py`
- `AI/app/domain/orchestration/delegation/*`
- `AI/app/cli/ui/tasks_browser.py`
- `AI/tests/api/test_tasks_runtime.py`
- `AI/tests/test_cli.py`
- `AI/tests/tools/test_notion_executor.py`

파일별 변경 이유:

- `tool_calling_loop.py`, `delegation/*`: child session 진입 key를 executor 기준으로 넘긴다.
- `tasks_browser.py`: 상세 화면 표시를 `executor`와 `entry_executor_key` 기준으로 맞춘다.
- 테스트 파일들: 새 API/fixture 기준을 고정하고 legacy fallback 만 별도 테스트로 남긴다.

구현 내용:

- child session payload 에 `entry_executor_key`를 사용한다.
- CLI detail 화면은 `entry_executor_key` 우선으로 표시한다.
- API 테스트는 새 응답의 `entry_executor_key`를 확인한다.

검증 방법:

- 전체 테스트 실행.

완료 기준:

- 실행 경로의 canonical 입력/출력은 executor 명칭만 사용한다.
- app/test 코드에서는 이전 진입 필드명을 사용하지 않는다.

## 이후 필요한 작업

## 1. 운영 DB 연결 시 schema baseline 재확인

- 필요한 이유: 지금은 운영 DB가 없어서 schema 를 바로 정리했지만, 실제 DB를 붙일 때 baseline 과 migration 순서를 다시 확인해야 한다.
- 추천 순서: 실제 DB 생성/초기화 경로를 확인한 뒤 migration id 정책을 고정한다.
- 관련 파일: `AI/app/storage/queries/task_queries.py`, `AI/app/storage/sqlite/repository.py`

## 2. executor registry 확장 기준 정리

- 필요한 이유: 다음 executor가 늘어나면 intent 기본 executor와 명시 executor 선택 규칙이 중요해진다.
- 추천 순서: executor 등록 문서와 테스트를 먼저 추가한 뒤 구현체를 늘린다.
- 관련 파일: `AI/app/tools/registry/registry.py`, `AI/app/tools/contracts.py`

## 메모

- 현재 기준은 “새 구조와 DB schema 모두 executor만 노출”이다.
