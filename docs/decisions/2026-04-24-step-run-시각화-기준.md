# StepRun 시각화 기준 결정

## 배경

현재 백본은 `TaskRun` 아래에 `StepRun`을 두고, 각 `StepRun.detail_json` 안에 `semanticDetail`, `operationDetail`, `toolDetail`, `approvalDetail` 같은 실행 메타데이터를 누적한다.

문제는 `semantic step`을 별도 상위 개념으로 키우면 다음 혼선이 생긴다는 점이다.

- 화면 기준 단위가 `StepRun`인지 `semantic step`인지 불명확해진다.
- tool 호출이 많아질수록 같은 의미 단계 안에서 불필요하게 여러 `StepRun`이 생길 위험이 있다.
- approval resume, todo projection, child task linkage 처럼 이미 `StepRun`이 anchor 역할을 하는 구조와 중복된다.

## 결정

### 1. 화면과 이벤트의 기준 단위는 `StepRun`이다

- UI 카드, API step 목록, step detail 화면은 모두 `StepRun` 기준으로 제공한다.
- `semantic step`은 별도 엔티티나 별도 리스트 단위로 분리하지 않는다.

### 2. 의미 정보는 `StepRun` 내부에 유지한다

- `semanticDetail`은 `StepRun.detail_json` 안에 유지한다.
- 포함 항목:
  - `semanticKey`
  - `semanticStep`
  - `goal`
  - `lifecycle`
  - `status`
  - `anchorStepRunId`

즉 `semantic`은 "이 `StepRun`이 사용자에게 어떤 의미 단계로 보이는가"를 설명하는 메타데이터다.

### 3. 한 `StepRun` 안에 여러 tool/llm operation 이 들어갈 수 있다

- tool 호출마다 새 `StepRun`을 만들지 않는다.
- 같은 사용자 의미 단계 안에서 발생한 tool 호출, llm 호출, mapping, summarize, finalize 는 모두 `operationDetail.operations`에 누적한다.
- `toolDetail.toolNames`는 중복 제거된 대표 사용 tool 목록을 유지한다.
- `llmDetail.callCount`는 같은 `StepRun` 안에서 누적 증가한다.

### 4. 새 `StepRun`은 "경계"가 생길 때만 만든다

새 `StepRun` 생성 조건:

- 새 task 진입 시 첫 anchor step 생성
- 사용자에게 별도 단계로 보여야 하는 todo projection 생성
- 완전히 다른 사용자 의미 단계로 넘어가는 명시적 planner transition
- 별도 task 로 분리되는 child task 는 자식 task 안에서 새 `StepRun`을 가짐

새 `StepRun`을 만들지 않는 조건:

- 같은 단계 안의 tool 호출
- 같은 단계 안의 llm 재호출
- mapping / summarize / finalize 같은 내부 operation
- approval waiting 이후 resume

approval resume 는 기존 `StepRun`을 재사용해야 한다.

## 사용자 흐름에서의 의미

사용자 흐름으로 보면 이번 기준은 아래처럼 해석한다.

- 사용자가 작업 하나를 시작하면 화면에는 `StepRun` 카드 하나가 생긴다.
- 그 안에서 모델이 여러 번 생각하고, tool을 여러 번 부르고, 승인을 기다렸다가 다시 이어도, 그걸 작은 카드 여러 개로 쪼개지 않는다.
- 즉 사용자 입장에서는 "한 단계 안에서 무슨 일이 있었는지"를 계속 같은 카드에서 보게 된다.

예를 들면:

- 예전 문제: `skills.list`를 두 번 부르면 이전 기록이 덮여서 한 번만 보일 수 있었다.
- 현재 기준: 같은 step 안에 `tool.skills.list.1`, `tool.skills.list.2`처럼 둘 다 남는다.
- approval도 새 step을 만드는 게 아니라 같은 step이 `WAITING -> RUNNING -> COMPLETED`로 이어진다.

사용자에게 보이는 효과:

- 단계 카드가 덜 흔들린다.
- "왜 step이 갑자기 여러 개 생겼지?"가 줄어든다.
- 같은 단계 안의 tool/LLM 활동 내역이 더 정확하게 누적된다.
- 승인 후 재개도 같은 단계가 이어지는 흐름으로 보인다.

## 의미 기준 해석

핵심 기준은 "단순 작업 몇 개를 묶는가"가 아니라 "사용자에게 같은 의미 단계로 보이는가"다.

- 의미가 비슷한 여러 단순 작업은 하나의 `StepRun`으로 묶어 시각화할 수 있다.
- 그 경우 내부 실행 조각은 별도 `StepRun`이 아니라 `operation`으로 누적한다.
- 즉 `StepRun`은 "의미 단위 카드", `operation`은 "그 카드 안의 실행 조각"으로 본다.

예:

- 입력 정리
- 모델 호출
- 결과 요약

이 세 개가 사용자에게 "응답 생성"이라는 하나의 단계로 보인다면, 하나의 `StepRun` 안에 들어갈 수 있다.

반대로 사용자에게 분명히 다른 단계로 보이는 경우에는 별도 `StepRun`을 만드는 편이 맞다.

## 서브에이전트 확장 해석

나중에 서브에이전트가 구현되더라도 같은 기준을 적용할 수 있다.

- 부모 입장에서 서브에이전트 호출 전체를 "하나의 위임 단계"로 보여 주고 싶다면, 그것을 하나의 `StepRun`으로 둘 수 있다.
- 이 경우 부모 step 안에는 delegation 관련 operation 과 `agentDetail.childTaskRunId` 같은 linkage 정보가 들어간다.
- 실제 자식 task 내부에서는 자식 task 나름의 `StepRun`들이 따로 존재할 수 있다.

즉 시각화 관점에서는:

- 부모 화면: "서브에이전트에게 맡김"이라는 하나의 `StepRun`
- 자식 상세 화면: 그 안의 세부 `StepRun`들

이런 2단 구조가 가능하다.

결론적으로, 서브에이전트도 반드시 별도 step 여러 개로 바로 노출해야 하는 것은 아니다.
부모 사용자 흐름에서 하나의 의미 단계로 보고 싶다면 하나의 `StepRun`으로 표현할 수 있다.

## 구현 원칙

### A. StepRun boundary 정책을 별도 규칙으로 분리한다

현재 `semanticKey` 관련 헬퍼는 있으나, 실제로 "언제 새 `StepRun`을 열 것인가"를 강하게 통제하는 정책은 없다.

추가 방향:

- `StepRunBoundaryPolicy` 또는 유사한 helper 를 둔다.
- 입력:
  - 현재 step
  - 다음 executor / todo item / transition reason
  - 독립 anchor 필요 여부
- 출력:
  - `reuse_current_step`
  - `create_new_step`
  - `reuse_for_resume`

핵심은 `semanticKey`만으로 새 step 을 만들지 않고, "사용자에게 별도 단계로 보이는가"와 "독립 anchor 가 필요한가"를 같이 판단하는 것이다.

### B. operation key 는 invocation 단위로 고유해야 한다

현재 tool loop 는 tool 이름 자체를 operation key 로 사용한다.
이 구조는 같은 tool 을 두 번 호출하면 이전 operation 을 덮어쓸 수 있다.

개선 방향:

- tool 호출:
  - `tool.skills.list.1`
  - `tool.skills.list.2`
- llm 호출:
  - `llm.generate.1`
  - `llm.generate.2`
- approval:
  - `approval.request.1`
  - `approval.resume.1`

이렇게 하면 한 `StepRun` 안의 실제 실행 흐름을 잃지 않고 누적할 수 있다.

### C. API step view model 추가는 보류한다

현재 API 는 `StepRunResponse.detail_json`을 그대로 노출한다.
시각화가 `StepRun` 기준으로 굳어질수록, 클라이언트가 raw dict 를 직접 해석하지 않아도 되게 정규화된 view 를 같이 주는 편이 낫다.
다만 현재 단계에서는 응답 스키마를 늘리기보다 `detail_json`을 그대로 유지하고, 실제 UI 요구가 생길 때 추가한다.

나중에 필요해지면 아래 같은 응답 구조를 검토한다.

```json
{
  "step_run_id": "step_123",
  "step_order": 1,
  "step_type": "model.generate.execute",
  "status": "RUNNING",
  "title": "모델 응답 생성",
  "view": {
    "displayTitle": "모델 응답 생성",
    "displayStatus": "partially_completed",
    "semantic": {
      "key": "response.compose",
      "step": "모델 응답 생성",
      "goal": "사용자 요청을 바탕으로 최종 모델 응답을 생성한다."
    },
    "tools": {
      "primary": "skills.list",
      "names": ["skills.list", "terminal.run"]
    },
    "llm": {
      "model": "gpt-5.4",
      "callCount": 2
    },
    "operations": {
      "totalCount": 5,
      "completedCount": 3,
      "runningCount": 1,
      "waitingCount": 1,
      "items": []
    },
    "approval": {
      "requested": true,
      "approvalId": "approval_123"
    }
  },
  "detail_json": {}
}
```

현재 결정:

- `StepRunResponse`에는 `view`를 추가하지 않는다.
- API와 CLI는 당분간 `detail_json`을 기준으로 동작한다.
- `view`는 프런트나 외부 클라이언트 요구가 명확해질 때 다시 검토한다.

### D. CLI 의 `view` 전환도 함께 보류한다

`tasks_browser`는 현재 `detail_json`을 직접 해석한다.
API에 `view`가 추가되면 CLI 역시 그 구조를 우선 사용할 수 있다.
하지만 현재는 `detail_json`을 디버그와 시각화의 단일 기준으로 유지한다.

### E. top-level workflow 단계는 task-level plan 으로 심고 순차 handoff 한다

복수의 의미 단계를 가진 사용자 요청은 바로 여러 executor 로 자동 전환하지 않아도, 먼저 top-level workflow plan 으로 표현할 수 있다.

- 현재 anchor `StepRun`은 plan 의 첫 단계다.
- 남은 단계들은 `task.todo_state`에 별도 semantic step 후보로 저장한다.
- task engine 은 이 남은 단계들을 todo projection step 으로 시각화할 수 있다.
- 이렇게 하면 현재 step 과 미래 step 을 같은 화면에서 안정적으로 보여 줄 수 있다.

예를 들어 사용자가 아래처럼 요청했다고 하자.

- "나 지금 하고 있는 작업 커밋하고 내용 정리해서 문서 정리한 다음에 노션에 API 명세 넣어줘"

이 경우 top-level plan 은 아래처럼 잡을 수 있다.

- `StepRun 1`: 작업 커밋 분석 및 준비
- `StepRun 2`: 변경 내용 정리
- `StepRun 3`: 문서 정리
- `StepRun 4`: Notion API 명세 반영
- `StepRun 5`: 결과 반환

여기서 중요한 점은:

- 현재 anchor `StepRun`이 끝나면, 남아 있는 pending workflow step 중 다음 항목을 실제 current step 으로 승격할 수 있다.
- 이때 future todo 로 먼저 만들어 둔 projected step 을 재사용해서 같은 카드가 `PENDING -> RUNNING -> COMPLETED`로 이어지게 한다.
- plan step 이 `entryExecutorKey` 또는 `intentType`을 가지면, 다음 단계는 그 executor 로 라우팅한다.
- handoff 시점에는 이전 step 결과를 다음 step 입력에 붙여서 이어서 실행한다.

즉 현재 구현은:

- top-level workflow plan 생성
- future step projection
- projected step 재사용
- step 간 기본 handoff
- step 별 executor routing

까지 포함한다.

아직 없는 것은:

- 복잡한 branching/조건 분기
- step 실패 시 rollback/retry policy
- handoff payload 정규 스키마
- planner 가 동적으로 새 plan step 을 추가하는 기능

## 결론

- `StepRun`을 사용자 시각화의 1급 단위로 고정한다.
- `semantic`은 `StepRun` 내부 설명 메타데이터로 유지한다.
- tool/llm/approval 같은 실행 조각은 같은 `StepRun` 안에 operation 으로 누적한다.
- 새 `StepRun`은 정말 별도 단계 경계가 생길 때만 만든다.
- 정규화된 `step view model` 추가는 지금 하지 않고, 필요가 확인될 때까지 보류한다.
