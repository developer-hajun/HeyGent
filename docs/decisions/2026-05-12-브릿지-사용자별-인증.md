# 브릿지 사용자별 인증 설계 결정

## 날짜

2026-05-12

## 작성자

이승엽

## 배경

기존 브릿지(`bridge/`)는 PoC 단계라 AI 서버 `.env` 의 단일 공유 토큰(`HEYGENT_BRIDGE_TOKEN`)을 모든 사용자 PC 가 동일하게 사용했습니다. 누가 띄워도 같은 슬롯에 들어갔고 사용자 식별이 없었습니다. 또한 URL 이 `ws://localhost:8000` 기본이라 배포 환경에서 검증되지 않았습니다.

서비스 단계로 가려면 두 가지가 동시에 필요합니다.

1. 사용자가 자기 PC 만 자기 계정에 묶을 수 있어야 합니다.
2. 브릿지가 `wss://` 배포 도메인에서도 정상 동작해야 합니다.

## 채택한 설계

### 인증 방식: 페어링 코드 (6자리, TTL 5분)

- backend 가 로그인된 사용자에게 `/api/v1/bridge/pairing` 으로 6자리 숫자 코드를 발급합니다. Redis 에 5분 TTL.
- 브릿지 PC 는 GUI 에 코드와 디바이스 이름을 입력하고 `/api/v1/bridge/pair` 로 교환합니다. 이때 무인증으로 호출하지만, 코드가 사용자 본인을 입증합니다.
- 응답으로 받은 `bridgeToken` 은 SHA-256 해시만 Postgres `bridge_devices.token_hash` 에 저장되며, 원본은 사용자 PC 의 `%LOCALAPPDATA%/HeyGent/bridge.json` (또는 macOS/Linux 등가 경로) 에 영구 저장됩니다.

채택 이유:

- OAuth 콜백 흐름을 브릿지 GUI 에 끼우는 비용이 큽니다 (카카오 콘솔에 localhost redirect_uri 등록 등).
- 수동 토큰 복사·붙여넣기는 UX 가 나쁩니다.
- 페어링 코드는 IoT 디바이스에서 이미 검증된 패턴(`DevicePairingRedisRepository`)이라 같은 Redis 패턴을 재사용할 수 있습니다.

### 1 user → 1 슬롯

- 한 사용자가 동시에 여러 PC 에서 브릿지를 띄울 수 없습니다.
- 새 페어링이 성공하면 그 user 의 기존 활성 디바이스를 모두 `revokedAt` 채워서 폐기합니다. AI 서버의 `BridgeSessionManager` 도 같은 user 의 기존 WebSocket 을 끊고 새 연결로 교체합니다.
- 다중 PC 시 어디로 도구 위임할지 고르는 UX 가 복잡해서, 1차에는 1슬롯으로 단순화합니다.

### 토큰 수명: 무기한

- 한 번 페어링하면 사용자가 웹 대시보드에서 명시적으로 해제하기 전까지 유지됩니다.
- 브릿지는 PC 부팅 후 항상 켜져 있는 게 자연스러우므로 30일 만료 같은 자동 갱신 정책은 UX 마찰이 더 큽니다.
- 보안은 SHA-256 hash 저장 + 1슬롯 정책 + 사용자 본인의 명시 폐기로 처리합니다.

### 검증 경로: AI → backend internal

- 브릿지 hello 메시지의 토큰을 AI 서버가 그대로 신뢰하지 않고 backend `/internal/bridge/auth/validate` 에 위임 검증합니다. AI 가 브라우저용 `auth.start` 흐름에서 backend 에 JWT 검증을 외주하는 패턴과 동일합니다.
- internal 엔드포인트는 기존 `HEYGENT_INTERNAL_SERVICE_TOKEN` 으로 보호하며, `AiInternalAuthenticationFilter` 의 적용 prefix 를 `/internal/ai/` → `/internal/` 로 넓혀 일괄 보호합니다.

### 배포·로컬 선택

- 브릿지 GUI 에 환경 라디오 (로컬/배포) 를 두고 두 프리셋 URL 을 코드에 박아둡니다.
- `.env` 또는 환경변수의 `BRIDGE_AI_WS_URL`, `BRIDGE_API_BASE_URL` 이 있으면 항상 우선합니다 (개발자가 임의 도메인 박을 수 있게).
- `wss://` URL 은 `ssl.create_default_context()` 로 시스템 루트 CA 검증.

## 검토했지만 채택하지 않은 옵션

- **카카오 OAuth in 브릿지 GUI:** redirect_uri 등록 + 로컬 callback 서버 + 토큰 저장까지 구현 부담 큼.
- **수동 토큰 복사·붙여넣기:** UX 나쁨.
- **사용자별 1회용 액세스 토큰을 매번 갱신:** 브릿지는 상주 프로그램이라 갱신 마찰이 큼. 단일 토큰 무기한이 더 자연스러움.
- **backend WS 를 통한 proxy:** AI 서버에 추가 인프라 부담. 토큰 검증만 backend 가 맡고 데이터 경로는 AI 직결을 유지하는 게 더 단순.
