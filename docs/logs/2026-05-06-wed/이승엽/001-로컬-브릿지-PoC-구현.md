## 작업 목적

클라우드 AI 서버가 사용자 PC 자원(셸·파일)에 직접 접근하지 않고, 사용자 PC에서 도는 "로컬 브릿지" 프로그램에 위임하는 구조를 PoC 수준에서 구현한다.

배경: 현재 AI 서버는 `terminal.run`/`read_file`/`write_file`/`patch`/`search_files` 같은 로컬 자원 도구를 자기 컨테이너 안에서 직접 실행한다. 클라우드 배포 시 이 도구들은 사용자 PC가 아니라 클라우드 컨테이너 자원에 접근하게 되어 본래 의도(사용자 환경에서 실행)와 어긋난다. 반대로 사용자 PC에 클라우드가 직접 연결을 뚫으면 보안 위험이 크다. 그 사이의 안전한 다리로 **사용자 PC에서 도는 별도 프로그램(브릿지)**을 둔다.

## 변경 요약

### AI 서버 측 (`ai/app/`)

- **`api/ws/bridge_gateway.py` 신규** — 브릿지 전용 WebSocket 엔드포인트 `/ai/api/v1/internal/bridge/ws`. `bridge.hello`/`bridge.ack` 로 토큰 인증, `tool.invoke`/`tool.result` 로 도구 위임, `ping`/`pong` 으로 연결 유지
- **`bridge/bridge_session.py` 신규** — `BridgeSessionManager` (단일 슬롯). 메인 이벤트 루프 바인딩 후, 동기 컨텍스트(`run_call`)에서 `execute_sync`로 위임 호출 가능
- **`tools/runtime/local_tool_runtime.py`** — `BRIDGE_ROUTABLE_TOOLS = {"terminal.run", "read_file", "write_file", "patch", "search_files"}` 분기 한 곳 추가, `_maybe_route_via_bridge` 헬퍼 추가. 결과 dict 형식은 기존 로컬 실행과 100% 동일하게 유지(외부 호출자는 분기를 인지 못함)
- **`domain/orchestration/agent/tool_calling_loop.py`** — `_execute_native` 안의 동기 `_run_native_tool_call` 호출을 `await asyncio.to_thread(...)`로 감쌈. 브릿지 위임 시 메인 이벤트 루프와 동기 차단이 만나는 데드락을 회피
- **`api/router.py`** — `bridge_ws_router` 등록
- **`core/config.py`** — `bridge_token` 설정 추가 (`HEYGENT_BRIDGE_TOKEN`)
- **`main.py`** — lifespan에서 `BridgeSessionManager` 인스턴스화·이벤트 루프 바인딩·`LocalToolRuntime`에 주입·`app.state` 등록

### 브릿지 측 (`bridge/` 신규 폴더)

- **`main.py`** — 콘솔 모드. WebSocket client. `bridge.hello` 인증, `tool.invoke` 수신 시 `_handle_tool_invoke`가 `asyncio.to_thread`로 executor 호출 후 `tool.result` 반환. `websockets.connect(ping_interval=...)` 로 docker NAT idle 끊김 회피
- **`tray.py`** — 트레이 모드. 시작 시 customtkinter 다크 GUI로 워크스페이스 폴더 선택, [시작] 후 시스템 트레이에 H 아이콘. 상태/폴더 표시, 워크스페이스 열기, 종료 메뉴
- **`executor.py`** — `terminal.run` + 파일 도구 4개를 사용자 PC에서 실행. AI 서버 측 결과 dict 형식 그대로 반환
- **`_file_tools.py`** — AI 서버 `app/tools/file/file_tools.py` 사본. `register_runtime_tool_definition` 만 더미로 교체, 나머지는 동일. 결과 형식 일치 보장
- **`config.py`** — `.env` 로딩
- **`.env.example`** — 환경변수 템플릿
- **`requirements.txt`** — `websockets`, `pystray`, `Pillow`, `customtkinter`
- **`README.md`** — 설치·실행·동작 확인·자주 막히는 곳 가이드

## 결정 / 이슈 / 리스크

### 결정
- 브릿지 라우팅 자리는 `LocalToolRuntime.run_call` **단 한 곳**. 다른 호출자는 결과 dict 형식이 같으면 분기를 인지할 필요 없음
- 브릿지 인증은 단순 공유 토큰 비교(`HEYGENT_BRIDGE_TOKEN` ↔ `BRIDGE_TOKEN`). backend 검증 미경유 — **PoC 단축**, 운영 단계엔 backend가 사용자별로 발급·검증하는 구조로 가야 함
- 동기/비동기 경계: `tool_calling_loop._execute_native` 안의 `_run_native_tool_call` 호출을 `asyncio.to_thread`로 감쌈. `_resolve_pending_tool_after_resume`(approval resume 경로)는 동기 함수라 그대로 두고 후속 검증으로 남김
- 브릿지 file 도구는 AI 서버 `file_tools.py` 사본을 그대로 사용 → 결과 dict 형식 100% 일치 보장
- 트레이 GUI: customtkinter 다크 테마. 시작 다이얼로그에서 워크스페이스 폴더 확인 후 진입. 굴러가는 동안엔 폴더 변경 불가(끄고 다시 시작해야 적용)

### 이슈 (PoC 가정대로 박제)
- **단일 슬롯**: `BridgeSessionManager`는 동시에 1대 브릿지만 허용. 다중 사용자 대응 X
- **session_key 락**: 같은 session_key 재사용 시 active TaskRun 락이 안 풀려 두 번째 호출 409. 검증 시 매번 다른 키 사용으로 회피
- **한글 인코딩**: stdout/응답에 한글이 garble로 보이는 경우 있음 (Windows 콘솔 코드페이지 디테일). PoC 본질엔 영향 없음

### 리스크 / 향후 작업
- **인증/인가는 backend로 일원화**: 현재 브릿지 토큰은 AI 서버 자체 비교. 운영 시 backend가 사용자별 영구 토큰 발급 + AI 서버는 backend에 검증 위임. 디바이스 코드 플로우(Netflix 방식) UX 후보
- **사용자 ↔ 브릿지 매핑**: 단일 슬롯 → owner_key 기반 dict로 확장 필요
- **배포**: PyInstaller로 .exe 패키징 후 GitLab Releases 게시 (일반 사용자가 Python·pip 안 깔고 더블클릭으로 실행 가능하게). 현재는 README 가이드 기반 개발자 셋업
- **브라우저 도구(`browser_*`)**: 현재 Camofox 별도 도커 컨테이너로 EC2 호스팅 가능. 사용자 PC 위임 시 무게 큼(설치 가이드 필요). 운영 단계 시나리오별 정책 결정 필요
- **HTTP 응답 타임아웃**: 긴 작업의 경우 `POST /taskRuns`가 응답을 끝까지 잡고 기다리는 구조라 timeout 위험. 추후 이벤트 스트리밍 단계에서 처리
