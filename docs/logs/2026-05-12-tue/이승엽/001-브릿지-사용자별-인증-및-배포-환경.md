## 작업 목적

브릿지 (사용자 PC 의 Python 프로그램) 를 두 가지 방향으로 한 번에 손봤습니다.

1. **사용자별 인증.** 기존 단일 공유 토큰 (`HEYGENT_BRIDGE_TOKEN`) 만 비교하던 PoC 구조에서, 각 사용자가 페어링 코드로 본인 PC 토큰을 발급받는 구조로 전환.
2. **배포 환경 동작.** 브릿지가 `wss://k14e105.p.ssafy.io/ai/api/v1/internal/bridge/ws` 같은 배포 도메인에도 붙을 수 있게 SSL 컨텍스트와 환경 프리셋 추가. 개발 중이라 로컬도 그대로 선택 가능.

## 변경 요약

### Backend (Spring Boot)

- 신규 도메인 `domain/bridge` 추가.
  - `BridgeDevice` 엔티티 (Postgres). `user_id`, `device_name`, `token_hash` (SHA-256), `last_seen_at`, `revoked_at` + Auditing 필드.
  - `BridgeDeviceRepository`, `BridgePairingRedisRepository`.
  - `BridgePairingSession` record (Redis 직렬화용).
  - DTO 6종: 페어링 코드 발급/교환, 디바이스 응답, internal validate 요청·응답.
- 컨트롤러 3종.
  - `BridgeController` (`/api/v1/bridge/pairing|devices`) — JWT 보호. 페어링 코드 발급(중복 방지), 디바이스 목록, 해제.
  - `BridgePairController` (`/api/v1/bridge/pair`) — 무인증. 브릿지 PC 에서 코드+디바이스명 → bridgeToken 교환.
  - `BridgeInternalAuthController` (`/internal/bridge/auth/validate`) — `ai.internal.token` 으로 보호. AI 가 hello 검증할 때 호출.
- `BridgeService` 가 1슬롯 정책을 강제. 새 페어링 성공 시 이 user 의 기존 활성 디바이스를 모두 revoke.
- internal 필터 prefix 를 `/internal/ai/` → `/internal/` 로 확장해 같은 토큰으로 bridge internal 도 보호.
- `SecurityConfig.permitAll` 에 `/api/v1/bridge/pair` 추가.
- `ErrorCode` 에 브릿지 전용 5개 추가.

### AI 서버 (FastAPI)

- `bridge_gateway.py` 의 hello 검증을 backend 외주로 교체. 단일 공유 토큰 비교 코드 제거.
- `BridgeSessionManager` 를 user 별 슬롯으로 재설계. `_sessions_by_user`, `_user_by_session` 두 dict. `is_alive(user_id)`, `execute_sync(user_id=...)` 시그니처.
- `LocalToolRuntime._maybe_route_via_bridge` 가 현재 요청의 `owner_key` (= backend user_id) 를 BridgeSessionManager 에 전달.
- `BackendAuthClient.verify_bridge_token()` 추가.
- `core/config.py` 에 `backend_bridge_auth_verify_url` 추가, `bridge_token` 은 deprecated 주석.

### Bridge (Python)

- `storage.py` 신설 — `%LOCALAPPDATA%/HeyGent/bridge.json` (또는 macOS/Linux 등가) 에 토큰/디바이스/환경 저장.
- `environments.py` 신설 — local/prod 두 프리셋 (`ws://localhost:8000` / `wss://k14e105.p.ssafy.io`). 기본 prod.
- `pairing.py` 신설 — 표준 라이브러리(urllib) 만으로 backend `/api/v1/bridge/pair` 호출.
- `config.py` 재작성 — 토큰 출처 우선순위(storage > env), `BRIDGE_ENVIRONMENT` 환경변수 지원, 토큰 필수 검사 제거.
- `main.py` — wss:// 면 `ssl.create_default_context()` 적용. hello 에 `device_name` 추가.
- `tray.py` 재작성 — 시작 다이얼로그에 환경 라디오 + 페어링 코드/디바이스 이름 입력 + "페어링 요청" 버튼. 트레이 메뉴에 "이 디바이스 페어링 해제" 추가.
- `.env.example` 갱신 — `BRIDGE_ENVIRONMENT`, `BRIDGE_API_BASE_URL` 안내. `BRIDGE_TOKEN` 은 비워두는 게 기본.

### Frontend (React)

- `apis/bridge.ts` 신설 — `issueBridgePairingCode`, `listBridgeDevices`, `revokeBridgeDevice`.
- `pages/BridgeSettingsPage.tsx` 신설 — 디바이스 목록 + 페어링 코드 모달 (큰 글씨 + 카운트다운 + 5초 폴링 자동 닫힘 + 코드 복사).
- `App.tsx` 에 `/settings/bridge` 라우트 추가.
- `LeftSidebar` ProfileMenu 에 "내 PC 브릿지" 한 줄 추가.

## 테스트 / 확인

이 별도 dev 폴더에서는 컴파일·타입 체크까지만 돌렸습니다. End-to-end 동작 확인은 별도 작업 폴더에서 진행 예정입니다.

- `./gradlew compileJava` — BUILD SUCCESSFUL
- AI 5개 핵심 모듈 `importlib.import_module` 모두 OK (런타임 회귀 사전 차단)
- Frontend `tsc -b` + `vite build` — 모두 통과
- Bridge 6개 변경 파일 AST 통과

미확인 (별도 작업 폴더에서 확인 필요):

- 실제 페어링 코드 발급 → 브릿지 GUI 입력 → 토큰 발급 → WebSocket hello → AI 가 backend 검증 → tool 실행까지 한 사이클.
- `wss://k14e105.p.ssafy.io` 인증서 검증이 Python `websockets` 에서 그대로 통과되는지.
- 같은 user 가 두 PC 에서 페어링했을 때 첫 번째 PC 의 토큰이 자동 폐기되고 두 번째 PC 로 슬롯이 옮겨가는지.
- 다른 user 의 브릿지가 같은 PC 에서 동시 실행돼도 슬롯이 섞이지 않는지.

## 결정 / 이슈

- 인증 방식은 페어링 코드(6자리, TTL 5분) 로 확정. 카카오 OAuth / 이메일 비번 / 수동 토큰 복사 옵션 모두 검토 후 UX 와 구현 부담 균형으로 채택.
- 토큰 수명은 무기한. 사용자가 웹 대시보드에서 명시적으로 해제할 때까지 유지. 토큰 hash 만 저장하므로 유출 시에도 원본은 복구 불가.
- 한 user 당 브릿지 1슬롯. 새 페어링이 들어오면 기존 활성 디바이스를 모두 revoke. 디바이스 row 자체는 폐기 이력 추적을 위해 보관.
- 디바이스 이름은 페어링 시 사용자가 GUI 에 직접 입력 (자동 호스트명 회수 안 함).
- 브릿지는 기존처럼 AI 서버 WebSocket 에 직접 붙는 구조 유지. 토큰 검증만 AI 가 backend 한테 외주.
- Frontend 는 별도 라우트 `/settings/bridge` 로 분리. 기존 SettingsDialog 에 손대지 않음.
