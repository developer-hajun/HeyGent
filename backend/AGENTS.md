# AGENTS

이 문서는 에이전트 사용 정책과 코드 스타일을 정의합니다.

## 정책

### 기본 원칙

- 사용자가 `코드수정해줘`라고 명시하기 전까지는 어떤 파일도 수정하지 않습니다.

### 항상 허용되는 작업

- 파일 및 코드 검색
- 파일 읽기 및 분석
- 설계 및 계획 수립
- 제안서 및 구현 방향 작성
- 성능, 아키텍처, 리팩터링 아이디어 제시

### 코드 수정 허용 트리거

- 사용자가 `코드수정해줘`라고 명시하면 그 시점부터 수정할 수 있습니다.
- 사용자는 수정 범위를 함께 지정할 수 있습니다.
- 예시: `코드수정해줘 backend/src/main/java/...`
- 범위를 지정하지 않으면 수정 범위는 현재 작업 루트인 `./` 하위로 제한합니다.

### 편집 범위 제한

- 현재 작업 루트와 하위 경로만 생성, 수정, 삭제를 허용합니다.
- 작업 루트 밖 경로는 조회만 허용하고 수정은 금지합니다.
- 작업 루트 밖 편집이 필요하면 반드시 사용자 명시 승인 후 진행합니다.
- 절대 경로 편집은 기본 금지이며, 사용자 승인 시에만 예외로 허용합니다.

### 변경 원칙

- 기존 코드 스타일과 패턴을 우선 따릅니다.
- 불필요한 설정 변경은 하지 않습니다.
- 영향 범위가 큰 변경은 사전 설명과 동의 후 진행합니다.

## 프로젝트 문서

백엔드 API는 프론트엔드와의 협업을 위해 항상 일관된 JSON 응답 계약을 유지해야 합니다.
공통 응답 및 예외 처리 방식은 아래 규약을 기준으로 맞춥니다.

## 공통 API 응답 및 예외 처리 규약

- 성공 응답은 Controller 계층에서 `ResponseEntity`를 직접 조립하기보다 공통 응답 래퍼를 우선 사용합니다.
- 반환 데이터가 있으면 `ApiResponse.success(data)` 형태를 우선 사용합니다.
- 반환 데이터가 없으면 `ApiResponse.success()` 또는 `ApiResponse.success(message, null)` 형태를 우선 사용합니다.
- 비즈니스 로직 실패는 Service 계층에서 `CustomException`을 throw 하고, 예외 응답 변환은 `GlobalExceptionHandler`에 위임합니다.
- Controller에서 성공 및 실패 응답 포맷을 제각각 직접 조립하지 않습니다.
- Controller에서 예외를 `try-catch`로 삼켜 임의 JSON을 반환하지 않습니다.
- 새로운 비즈니스 예외가 필요하면 예외 클래스를 임의로 늘리기보다 `ErrorCode` 확장을 우선 검토합니다.
- 클라이언트 입력값 검증은 Request DTO의 Bean Validation 어노테이션과 `@Valid`를 우선 사용합니다.
- 검증 실패 응답 포맷도 공통 예외 처리 규약을 따릅니다.
- Controller에서 동일 검증 로직을 중복 구현하지 않습니다.

### 공통 응답 계층 관련 메모

- 현재 저장소에는 공통 응답 및 예외 처리 클래스가 아직 없을 수 있습니다.
- 해당 계층을 도입하거나 확장할 때는 `ApiResponse`, `CustomException`, `ErrorCode`, `GlobalExceptionHandler` 중심의 일관된 구조를 유지합니다.
- 새 예외 메시지는 `ErrorCode`에서 상태 코드와 사용자 메시지를 함께 관리하는 방식을 우선 사용합니다.

## Swagger / OpenAPI 작업 규약

- Swagger 작업 시 기존 설정 클래스와 보안 설정을 먼저 확인합니다.
- 현재 프로젝트에 Swagger 설정 클래스가 없으면 기존 패키지 구조에 맞춰 추가합니다.
- 이 프로젝트의 API 기본 prefix는 `/api/v1`를 기준으로 합니다.
- Controller에는 필요 시 `@Tag`, `@Operation`, `@Parameter`, `@ApiResponses`, `@ApiResponse`를 사용합니다.
- DTO에는 필요 시 `@Schema`를 사용합니다.
- Swagger 작업만으로 비즈니스 로직, 응답 형식, 보안 설정은 바꾸지 않습니다.
- Swagger 설명도 공통 응답 규약을 기준으로 작성합니다.

## 명명 규칙

- 패키지명은 전부 소문자를 사용합니다.
- 클래스명과 인터페이스명은 PascalCase를 사용합니다.
- 메서드명은 camelCase를 사용합니다.
- 멤버 변수명은 camelCase를 사용합니다.
- 파라미터명은 camelCase를 사용합니다.
- 로컬 변수명은 camelCase를 사용합니다.
- `for` 루프 인덱스 등 짧은 생명주기 변수만 1글자 사용을 허용합니다.
- 약어는 과도한 대문자 연속 표기를 피합니다.

## 브랜치명 규칙

- 규칙: `타입/이슈키-설명`
- 예시: `BE-feat/로그인-구현`
- 예시: `BE-fix/CORS-수정`

## 커밋 메시지 규칙

- 규칙: `컴포넌트-작업타입 : 설명`
- 예시: `BE-feat : 로그인 API 구현`
- 예시: `BE-fix : WebMvcConfig CORS 설정 허용`
